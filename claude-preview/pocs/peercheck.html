01Le problèmeThe problem

Un de nos projets Holberton avait une Task 5 où les étudiants étaient censés valider leur propre travail. Mais ce projet-là nous paraissait différent : on voulait vraiment savoir si on avait bien fait, pas juste cocher une case. On en a parlé entre camarades et on était d'accord : un vrai retour structuré aurait été bien plus utile que l'auto-évaluation. Mon SWE m'a entendu le dire et s'est tourné vers moi en particulier : il savait que j'avais déjà plus de bagage sur les outils IA que le reste de la cohorte. « Adam, tu devrais faire la manual review toi-même. » C'est cette phrase qui est devenue l'idée.

One of our Holberton projects had a Task 5 where students were supposed to validate their own work. But this particular project felt different. We genuinely wanted to know if we'd done it right, not just tick a box. My classmates and I talked about it and agreed: a real structured review would have been far more useful than self-assessment. My SWE heard me say that and turned to me specifically: he knew I already had more background with AI tools than the rest of the cohort. “Adam, you should do the manual review yourself.” That comment became the idea.

02Mon approcheMy approach

J'ai construit une API Node.js qui lit un repo GitHub via la REST API, filtre les fichiers pertinents, et stream une review structurée en trois sections via Claude Haiku. Avant de générer quoi que ce soit, une validation en deux niveaux vérifie si le repo correspond bien à la Task AI-IDE : d'abord un scan de mots-clés à zéro token sur le README, puis un appel preflight Haiku qui rejette les repos sans rapport avec la task. Les repos invalides sont bloqués avant de consommer des tokens de génération. La review stream mot par mot via SSE, pour que les étudiants voient le retour apparaître progressivement.

I built a Node.js API that reads a GitHub repo through the REST API, filters the relevant files, and streams a structured three-section review using Claude Haiku. Before generating anything, a two-tier validation step checks whether the repo actually matches the AI-IDE task: first a zero-token keyword scan on the README, then a Haiku preflight call that rejects repos unrelated to the task. This way, invalid repos are blocked before consuming any generation tokens. The review streams word by word via SSE, so students see the output appear progressively rather than waiting for a full response.

03Le POCThe POC

Une API Node.js + Express déployée sur VPS derrière Nginx. SSE streaming pour que la review apparaisse mot par mot au fur et à mesure de la génération. Validation en deux niveaux : scan de mots-clés zéro token sur le README, puis appel preflight Haiku pour confirmer que le repo correspond à la Task AI-IDE. Maximum 900 tokens pour la review, 10 fichiers lus, 3000 caractères par fichier. La review est structurée en trois sections fixes : ce qui est bien, ce qui est à améliorer, ce qui n'est pas acquis. Envoi optionnel par email via Resend. Un AbortController stoppe le stream Claude immédiatement si l'étudiant ferme le navigateur. Une review complète tourne en moins de 10 secondes.

A Node.js + Express API deployed on VPS behind Nginx. SSE streaming so the review appears word by word as it generates. Two-tier validation: zero-token keyword check on the README, then a Haiku preflight call to confirm the repo matches the AI-IDE task. Max 900 tokens for the review, max 10 files read, 3000 characters per file. The review is structured in three fixed sections: what works, what to improve, what is not yet mastered. Optional email delivery via Resend. An AbortController stops the Claude stream immediately if the student closes the browser. A full review runs in under 10 seconds.

04Ce que j'en ai apprisWhat I took away

C'est la précision du périmètre qui rend le résultat fiable.

Constraining the scope is what makes the output trustworthy.

Le vrai travail, c'était de définir exactement ce que PeerCheck devait évaluer, et rien au-delà. C'est cette contrainte qui a rendu le feedback de l'IA vraiment utilisable. Je suis rentré dans ce projet sans savoir ce qu'était du SSE ni comment appeler une API. J'en suis sorti convaincu qu'un outil qui fait une seule chose bien produit des résultats dont on peut se porter garant.

The real work was defining exactly what PeerCheck should evaluate and nothing beyond that. That precision is what made the AI feedback actually usable. I went in knowing nothing about SSE or the Claude API. I came out convinced that a tool which does one thing well produces results you can stand behind.

05Ce que je ferais en prodWhat I'd do in prod

J'ajouterais un tableau de bord pour que l'enseignant puisse voir qui a soumis son repo et quand. J'éviterais de relancer l'IA sur le même repo deux fois si rien n'a changé. Si plusieurs étudiants soumettent en même temps, j'ajouterais une file d'attente pour ne pas cramer la limite d'API. L'objectif final, c'est que PeerCheck puisse reviewer n'importe quel repo GitHub, pas uniquement ce projet Holberton.

I'd add a dashboard for the teacher to see who submitted and when. I'd avoid re-running the AI on the same repo twice if nothing changed. If multiple students submit at the same time, I'd add a queue so requests don't pile up and hit the API limit. The real end goal is to make PeerCheck work for any GitHub repo, not just this one Holberton project.
